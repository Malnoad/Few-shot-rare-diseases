## 3. New weaknesses

### N-1. Image size alone almost solves the benchmark

**Problem.** The five rare classes can be told apart from the pixel dimensions of the files,
with no image content. Any five-way score on this benchmark has a floor that needs no encoder.

**Evidence** (`geo3.py`, on `geom.json`):
- Leave-one-out nearest centroid on raw (width, height) of the 124 development images:
  25/27, 25/26, 20/25, 1/19, 15/27 correct for CSC/MH/MacTel/Stargardt/RP; macro recall 0.659
  (chance 0.20).
- Centroids from all 124 development images applied to the legacy 22: 5/5, 5/5, 4/4, 0/4, 3/4;
  macro recall 0.75.
- With one random support per class the legacy macro recall is still about 0.63 (200 random
  draws, illustrative; these are not the locked episodes).
- Median width of the development images is 414/327/482/410/393 px by class, and every rare image is an RGBA PNG crop
  with black border bands (`geom.py` output; 146 of 146 RGBA, alpha fully opaque).

All arms resize, so absolute size is not directly visible to an encoder. Aspect ratio, blur
scale and the padding layout are. Whether the encoders use them is unknown; the point is that
a reviewer can compute this floor in minutes.

**Options.**
- A. Do nothing; keep the geometry table of A1 rule 4. Cost zero. The main five-way claim
  then has no answer to "is this better than file size?".
- B. Add a size-only reference row (recommended). About 40 lines of pure code and one test;
  no GPU, no new images. Width and height are already in `image_inventory.csv`
  (`fm_prepare.py:273`) and `external_inventory.csv` (`fm_external.py:39`).
- C. Normalize geometry (crop or pad every image the same way). Rejected: it changes every
  arm's native preprocessing, and the C0 audit found normalization did not remove the
  separation (`FM_EXTERNAL_MAPPING.md:113`).

**Recommendation (B), amendment text:** "Size-only reference. For every locked development
and reporting episode, each query is assigned to the class whose support images have the
nearest mean (width, height) in pixels of the original file (squared Euclidean distance, ties
to the fixed class order). No pixel and no encoder is used. Its macro recall is reported per K
beside every arm, and for the OCTID two-way test. It is a diagnostic of the benchmark, is never
nominated, and is not an arm."

On OCTID it should sit at chance if all images share one size, which is exactly why the
OCTID test matters. This is the one addition I recommend despite the "no new arms" rule: it is
not an arm, and the five-way claim is hard to defend without it.

**Deadline:** before the lock. **Confidence:** high on the finding, medium on the exact form.
I would drop it only if Lam restricts the paper's claim to "relative order of encoders on this
benchmark" and states the 0.66 floor in the limitations instead.

### N-2. A1 rule 5 requires intervals that are neither defined nor implemented

**Evidence.** A1 rule 5 (`FM_AMENDMENTS.md:44-45`) requires OCTDL patient-cluster intervals and
OCTID image-level intervals. No `fm_*.py` file contains a bootstrap or an interval (`grep` for
`5000|bootstrap|cluster` returns nothing). The rule does not say which quantity gets an
interval, and "image-level interval" has no single meaning for a result averaged over 100
support draws. See B-3 for the decision.

### N-3. The lock does not bind which external rare cohorts enter

**Evidence.** Rare cohorts are admitted by a command-line flag given after the lock:
`fm_external.py:58-60` keeps a rare row only if `--mapping SOURCE:LABEL=EVIDENCE` was passed
(`fm_external.py:470-495`). The lock stores only free-text `eligibility` strings
(`fm_prepare.py:631`). A1 says the cohorts are "fixed now". Omitting one flag after the
development scores would silently drop a cohort.

**Recommendation, amendment text:** "The A1 cohorts are constants in the code. No command-line
option adds or removes a cohort." Implementation: replace the `mappings` argument by a constant
with the A1 evidence strings and delete the flag. This removes code. **Deadline:** before lock.
**Confidence:** high.

### N-4. The lock hashes five code files, so "decide before reporting" often means "before lock"

**Evidence.** `load_lock` refuses any change to `fm_core.py`, `fm_prepare.py`, `fm_extract.py`,
`fm_evaluate.py`, `fm_external.py`, `stage3_classifier.py` or the requirements files
(`fm_prepare.py:55-56`, `717-722`). Pilot identities must also equal the code at lock time
(`fm_prepare.py:653-654`). So:
- A-1, A-5, B-1, B-3, N-1, N-3 and the padding columns all need code in hashed files and are
  lock-blocking, even where the tracker says "before reporting".
- Code and amendments must be final **before the final timing pilots**, not just before the
  lock session. A later edit forces new pilots.
- Editing `fm_prepare.py` changes `preparation_code()` (`fm_prepare.py:96-97`), so `screen` and
  `freeze` must be rerun. They are byte-reproducible; the six hashes pinned in
  `colab_fm.ipynb:114-121` should come out unchanged and must be checked.

### N-5. Field of view differs by arm, class and split; the summary is not implemented

**Evidence** (`geom.py`, `geo2.py`). RETFound and DINOv2 resize the short edge to 256 and crop
224x224 (`fm_extract.py:367-368`; upstream `util/datasets.py:50-54`). MIRAGE and Inception
squash the whole image. Retained area for the crop arms is 0.74-0.77 for 512-wide scans and
rare crops, but 0.25 for 1536-wide Kermany scans. The share of Kermany images wider than 512 px
differs by class and split: NORMAL 33% in fitting and 6% in test; DME 10% and 44%. OCTDL images
at the documented sizes would retain about 0.28 (computed from the documented sizes, not from
images). Protocol section 5 already orders this to be recorded, and `geometry.csv` records it
per image, but no table by class and source is produced.

**Recommendation:** add one summary table (count, median and range of width, height, retained
fraction and the two padding numbers, by source, class and role). No new decision is needed;
it implements A1 rule 4. **Deadline:** before lock (code). **Confidence:** medium.

### Smaller findings

- **Alpha is harmless.** All 146 rare images are RGBA with alpha 255 everywhere, so the arms'
  different alpha handling cannot change pixels (`geom.py`).
- **The duplicate screen will not explode.** Among 250 Kermany NORMAL test and 4,124 fitting
  images the dHash rule flags 5 pairs, all same-patient (`dhash_proxy.py`). A flood of flags
  for external NORMAL scans is unlikely, though unverified on the real images.
- **The timing inventory holds no Stargardt image** (27 CSC, 26 MH, 25 MacTel, 22 RP), because
  it is the first 100 sorted paths. This matches protocol section 7; no action.
- **A2's A-7 sentence** "matches each model's own frozen-encoder path" is true for MIRAGE only
  if the input transform also follows that path. This ties A-7 to A-11.

## 4. Every tracker item

### A-1. OCTID two-way CSC-versus-MH test

**Problem.** A1 rule 3 names the test; the code does not produce it. `transfer_episodes`
(`fm_external.py:292-297`) runs the five-way head only.

**Evidence.** Each class centroid uses only its own supports (`fm_core.py:193-195`). A two-way
prototype refit therefore equals taking the larger of the `cosine_CSC` and `cosine_MH` columns
of the five-way episode. Checked on 10,000 random queries: identical (`equiv.py`).

**Options.** A: new two-class episode type (more code, new artifacts). B: derive the two-way
result from the saved five-way cosine columns in `summarize` (about 20 lines, one test).

**Recommendation (B), amendment text to add to A2's A-1:** "The two-way prediction is the larger
of the CSC and MH cosine scores of the locked five-way reporting episode, which equals refitting
with CSC and MH supports only. Chance is 0.50; a collapse to one class is reported as such. If
no nominee exists, all arms are reported without a headline. The logistic probe is never used
for this test; for the five-way output shares it stays as in v1.0 (first 25 draws per K)."

I agree with the A2 definition. The last sentence settles an ambiguity: A1 rule 3 bans the
probe only for the two-way test, and the existing code already runs it for the five-way shares.
Dropping it everywhere on external data is also defensible (v1.0 section 2 allows a dated
reduction) but costs test changes for no gain. **Deadline:** before lock. **Confidence:** high.

### A-11. Input preprocessing

**Evidence.**
- MIRAGE linear-probe benchmark: resize bilinear, grayscale, then `MinMaxNormChannel`
  (`fm_cls_config.py:77-84, 150-154` at `ee5eae8d`). Paper: "For MIRAGE, min-max normalization
  was applied to the input images" (PMC12462498).
- MIRAGE demo and pretraining: divide by 255 only (`hf/mirage_hf.py:115-119`;
  `mirage_wrapper.py:261-264`; `mutils/datasets_pretrain.py:187-189`, fetched today into `up/`).
- Local images: every Kermany image in the roster already reaches 255, so min-max changes
  almost nothing there. Among rare development images 26% (CSC) to 78% (RP) do not reach 255,
  so min-max changes them (`geo2.py`). Neither option is neutral across classes.
- RETFound: our transform equals `util/datasets.py:50-56`, used for its fine-tune and
  linear-probe runs.

**Options.** A: keep /255 (no code change; matches pretraining and the model card demo).
B: add min-max (one line and a test; matches the published frozen-probe path). C: both
(rejected: doubles an arm and invites choosing after scores).

**Recommendation (B), amendment text:** "Each encoder uses the input transform of its own
published frozen-probe code path at the pinned commit. MIRAGE: resize 512x512 bilinear,
grayscale, divide by 255, then (x - min) / (max - min) over the image; an image with max = min
stops the arm. RETFound and DINOv2 are unchanged."

I agree with B, for a different main reason: A2 already takes MIRAGE's pooling and norm from
that same benchmark path (A-7), and mixing it with the demo's input transform would be a hybrid
no upstream code runs. **Deadline:** before lock; Lam decides. **Confidence:** medium. A
statement by the MIRAGE authors that /255 is intended for frozen features would change my mind.
If Lam prefers zero code change, A is defensible, but the A-7 sentence must then be reworded.

### Padding definition (A1 rule 4)

**Evidence** (`geom.py`). The previous definition (complete border rows or columns of one
constant value) gives a median of 0.000 for every Kermany class, because Kermany's white fill
is wedge-shaped; yet 54-82% of Kermany images have more than 1% of pixels at 250 or above. It
gives 0.27-0.42 for the rare classes. It also needs exact equality, which JPEG sources break.

**Recommendation, amendment text:** "Two label-free numbers per image, on the decoded 8-bit
grayscale original: (1) border share: the share of area in complete border rows and columns,
peeled from each edge, whose grey range is at most 8; (2) near-white share: the share of pixels
at 250 or above. Both are reported by class and source with width and height. They are
descriptive and gate nothing." Local values: border share median 0.34-0.50 for the rare
classes and 0.00 for Kermany; 94.5% of rare and 6.4% of Kermany images exceed 0.10.
**Deadline:** before lock. **Confidence:** high that the old definition fails, medium on the
thresholds.
